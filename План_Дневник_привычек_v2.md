## 1. Статус и что изменилось относительно v1

v1 описывал только путь «прототип → Telegram Mini App» и оставлял за скобками 850 пунктов улучшений качества. Это давало две ошибки в планировании:

1. **Двойная работа.** Многие пункты аудита (разбиение на модули, IndexedDB, тесты стриков, экранирование, `try/catch` вокруг `window.Telegram`) — это не «потом», а естественная часть переноса. Если делать их отдельным спринтом «стабилизация прототипа», половину придётся переделать после переезда на Vite + TS.
2. **Невидимый объём.** Без явной привязки пунктов к этапам срок «7–8 недель» выглядел оптимистично: он не учитывал ни доступность, ни безопасность, ни полировку UX.

Поэтому v2 не складывает два плана рядом, а **растворяет чек-лист внутри этапов**: у каждого этапа теперь есть список закрываемых пунктов roadmap. Сводная нумерация сохранена (001–850), полный чек-лист — в приложении.

## 2. Три контура работы

| Контур | Что это | Объём | Где в плане |
|---|---|---|---|
| **A. Качество прототипа** | 850 пунктов аудита: производительность, доступность, UX, психология привычек, архитектура JS, безопасность, данные | 850 задач | Распределены по этапам 1–7 (раздел 6) |
| **B. Перенос в Telegram** | Mini App: Vite + TS, Telegram SDK, экраны, механики, аналитика, постер | ~7–8 недель соло | Этапы 0–7 (раздел 6) |
| **C. Бэкенд и бот** | Fastify + Postgres, initData-авторизация, синхронизация, grammY, напоминания | входит в этапы 1, 3, 4 | Раздел 4, 6 |

**Правило приоритета:** контур A не блокирует старт B. Сначала закрываются пункты, которые дешевле сделать *до* переезда (разбиение файла, константы, тесты расчётов), затем те, что возможны только *после* (CSP, IndexedDB, outbox, CloudStorage). Пункты с пометкой «prototype-only» (работа с одним `localStorage`-ключом) закрываются автоматически при этапе 3 и не планируются отдельно.

## 3. Что переиспользуем и что обязательно переписываем

**Готово и переносится почти 1:1 (ядро продукта):**
5 экранов (Сегодня / Ритуалы / Анализ / Мастерство / Опции), свайп-карусель + нижний «остров» навигации, механика Плана Б (двухуровневая норма), свайп-чек-ин (короткий → План Б, длинный → Норма, влево → пропуск), пульс энергии 1–5, фильтры по сферам, аккордеон завершённых, стрики, «Костёр» (% дня), щиты, граница суток, ритуалы-цепочки с таймером и мини-плеером, аналитика (успешность, спасённые дни, средняя энергия, тепловая карта года, дни недели, причины пропусков, архетип месяца, PNG-постер), полка мастерства 60 дней, капсула времени, инкогнито, экспорт/импорт JSON/CSV/MD/HD_SYNC, зачатки `WebApp.ready()/expand()` и `HapticFeedback`.

**Переписывается обязательно:**

| Проблема в прототипе | Почему блокер | Решение | Пункты roadmap |
|---|---|---|---|
| `localStorage`, один ключ, синхронный `stringify` на каждый клик | Telegram WebView (iOS) чистит хранилище | IndexedDB + сервер + журнал операций | 034, 049–052, 761–780 |
| Нет бэкенда | Нет синхронизации и напоминаний | API + Postgres, авторизация по `initData` | 651–700, 751–800 |
| Фейковый QR (`(r*c)%3`), нерабочая `#sync=`-ссылка | Обещанная функция не работает | Убрать QR из MVP, починить ссылку через БД | 781–800 |
| Захардкоженная дата «Среда, 11 нояб.» | Ломает доверие с первого экрана | Вычислять из `Date`/`Intl` с кэшем форматтеров | 046–048, 201–206 |
| `setInterval(1000)` в таймере | Таймер «замерзает» при блокировке экрана | Считать дельту по `Date.now()`/`performance.now()` | 041–043, 069–071 |
| Щит списывается без проверки `shielded` | Сжигает запас на один день | Идемпотентная проверка на сервере | 351–360, 671–680 |
| Нет «Духа» в фильтре, нет редактирования привычки | Нельзя исправить опечатку без удаления | Фильтр + экран редактирования | 201–250 |
| `new Date(dKey)` как UTC | Сдвиг дня недели западнее UTC | Даты строкой `YYYY-MM-DD` + `Intl` | 046–048, 751–770 |
| Монолитный `<script>` ~1 500 строк | Нельзя тестировать и кэшировать по частям | ES-модули + тесты | 014, 086–088, 501–560 |

## 4. Целевая архитектура (по существу без изменений)

```
Telegram (iOS / Android / Desktop / Web)
        │  initData (подпись)
        ▼
Mini App (статика: Cloudflare Pages / Netlify, HTTPS)
  ├─ UI: текущий HTML/CSS → Vite + TypeScript, модули вместо одного файла
  ├─ Стейт: store + IndexedDB (idb), очередь операций (outbox)
  ├─ Telegram SDK: themeParams, MainButton, BackButton, HapticFeedback,
  │                CloudStorage, shareToStory, BiometricManager
  └─ API-клиент (fetch, ретраи, идемпотентность по op_id)
        │
        ▼
Backend (Node 22 + Fastify, или Supabase) + Postgres
  ├─ проверка initData (HMAC-SHA256, hash, auth_date, срок жизни)
  ├─ REST: habits / checkins / day_logs / rituals / settings / analytics
  ├─ сервис стриков и щитов (единый источник правды)
  └─ планировщик напоминаний (cron + очередь)
        │
        ▼
Telegram Bot (grammY)
  ├─ /start → кнопка-меню, открытие Mini App
  ├─ вечерний дайджест с inline-кнопками (чек-ин без входа в приложение)
  ├─ напоминания по времени пользователя + «не пропускай дважды»
  ├─ капсула времени после 2 пропусков подряд
  └─ платежи (Telegram Stars) на этапе монетизации
```

**Стек:** фронт — Vite + TS + нативный CSS прототипа (без React на MVP); бэк — Node + Fastify + Postgres (managed: Supabase/Neon), либо целиком Supabase (таблицы + RLS + edge-функция для initData); бот — grammY.

### Модель данных MVP

| Таблица | Ключевые поля |
|---|---|
| `users` | `tg_id`, `tz`, `day_boundary_hour`, `created_at`, `plan` |
| `habits` | `id`, `user_id`, `title`, `icon`, `sphere`, `type(binary/counter)`, `trigger`, `norm`, `plan_b`, `keystone`, `incognito`, `capsule`, `archived_at`, `sort` |
| `day_logs` | `user_id`, `date` (YYYY-MM-DD), `energy`, `shielded`, `note` |
| `checkins` | `user_id`, `habit_id`, `date`, `status(full/plan_b/skip/counter)`, `value`, `skip_reason`, `ts`, `op_id` |
| `rituals` / `ritual_steps` | `id`, `user_id`, `title`, `icon`, `steps[]` (title, minutes, order) |
| `settings` | `user_id`, `haptic`, `notifications`, `digest_time`, `theme` |
| `sync_ops` | `op_id`, `user_id`, `payload`, `applied_at` — идемпотентность |

**Синхронизация (MVP, без CRDT):** мутация → IndexedDB + операция в outbox → при открытии и на `visibilitychange` outbox уходит пачками → конфликт `(habit_id, date)` решается «последняя запись по `ts`» → `sync_ops` защищает от дублей. Полный CRDT — только когда появятся совместные привычки и «Костры».

## 5. Как читать дорожную карту

У каждого этапа три части: **результат** (что должно работать), **задачи** (что пишем) и **пункты roadmap** (что закрываем). Номера — из полного чек-листа в приложении; диапазоны вида `201–250` означают «все пункты диапазона, приоритет внутри — по матрице из раздела 7».

Сквозные разделы (I и II — производительность и доступность) не вынесены в отдельный этап: их пункты закрываются внутри этапов 1–2 (архитектура разметки и модулей) и проверяются прогоном на этапе 7.

### Этап 0. Подготовка (3–5 дней)
- Зафиксировать scope MVP (раздел 9), всё остальное — в бэклог v1.1.
- Бот в @BotFather, Mini App, домен, HTTPS.
- Политика конфиденциальности + согласие на обработку данных (обязательно для Telegram; учесть выбор хостинга под РФ-аудиторию).

### Этап 1. Каркас Mini App + авторизация + БД (1,5 недели)
- Vite + TS; вынос CSS и JS из 3 393-строчного файла; разбиение `<script>` на модули `state / storage / habits / analytics / ui / gestures / player`; включить `'use strict'` и ES-модули.

- API `/auth` с валидацией `initData` (HMAC-SHA256, `auth_date`, срок жизни), сессия, middleware.
- Схема БД + миграции; CRUD привычек; экран создания и **редактирования** привычки.
- **Пункты:** 001–030 (вынос и минификация CSS/JS, `passive`, `rAF`-дебаунс скролла, `DocumentFragment`), 034, 049–052 (версия схемы хранения), 086–088 (модули), 101–140 (семантика, фокус, `aria`, контраст, размеры тапов), 501–560 (слои и тесты расчётов), 651–700 (валидация `initData`, `try/catch` вокруг `window.Telegram`, CSP).

### Этап 2. Перенос ядра механик (1,5–2 недели)

- Стрики и щиты — расчёт на сервере, идемпотентность щита (один щит на день).
- Граница суток и часовой пояс из `initData.user`/`Intl`; даты — строкой, форматтеры кэшируются.
- **Пункты:** 031–048 (кодирование, кэш форматтеров, `crypto.randomUUID()`), 141–200 (навигация с клавиатуры, `prefers-reduced-motion`, `prefers-reduced-transparency`, `100dvh`), 201–350 (UX-полировка карточек и шторок), 351–400 (правило двух дней, автоплан Б при низкой энергии, милстоуны, цена пропуска, прогноз стрика).

### Этап 3. Офлайн-first и миграция данных (1 неделя)
- IndexedDB-слой, outbox, ретраи, «мгновенный отклик без спиннеров», батчинг сохранений, `requestIdleCallback`.

## 9. Риски и как их снимаем

| Риск | Митигация |
|---|---|
