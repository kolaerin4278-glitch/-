# План 03: Бэкенд, авторизация Telegram `initData` и PostgreSQL

> **Этап roadmap:** Этап 1 (часть 2 — сервер и БД) · **Длительность:** 4–5 дней · **Зависимости:** [План 01](01_Подготовка_и_инфраструктура.md) (может идти параллельно с Планом 02)
> **Результат:** поднят API-сервер (Fastify + Postgres или Supabase), работает проверка подписи `initData`, настроены миграции, CRUD для привычек/логов/ритуалов и заголовки безопасности.

---

## 1. Ключевые задачи исполнения

1. **Схема БД и миграции (PostgreSQL):**
   - Создать таблицы: `users`, `habits`, `day_logs`, `checkins`, `rituals`, `ritual_steps`, `settings`, `sync_ops` (согласно модели данных из [Плана 00](00_Обзор_и_навигация.md)).
   - Предусмотреть `created_at` / `updated_at` на сущностях, `deleted_at` для мягкого удаления (корзина) и уникальные `id`.
   - Заложить индексы по `(user_id, date)` и уникальность `op_id` в `sync_ops` для идемпотентности.
2. **Авторизация через Telegram `initData` (`POST /auth`):**
   - Валидировать `Telegram.WebApp.initData` на сервере по алгоритму Telegram (HMAC-SHA256 с ключом `WebAppData` + `BOT_TOKEN`), сверять `hash`, `auth_date` и срок жизни сессии.
   - Выдавать короткоживущий session token / JWT и проверять его в auth-middleware на всех защищённых маршрутах.
3. **REST API (базовый CRUD и валидация):**
   - Маршруты для `habits`, `checkins`, `day_logs`, `rituals`, `settings`, `analytics`.
   - Жёсткая серверная валидация длины и формата полей (`icon`, `title`, `trigger`, `norm`, `planB`, `capsule`, `steps`, `minutes`).
4. **Заголовки безопасности:**
   - Настроить на уровне сервера/хостинга: CSP (без `unsafe-inline` где возможно), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy`.

## 3. Критерии готовности (Definition of Done)

- Миграции Postgres накатываются с нуля без ошибок.
- Поддельный или просроченный `initData` отклоняется со статусом `401`, валидный — создаёт/обновляет `users` по `tg_id` и возвращает сессию.
- CRUD-операции для привычек работают end-to-end с сохранением в Postgres и проверкой ограничений полей.
- В HTTP-ответах присутствуют `nosniff`, `Referrer-Policy`, `Permissions-Policy` и CSP.
